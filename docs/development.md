# Development procedures

> 日本語版は [development.ja.md](development.ja.md) を参照してください。

Procedures that analyze-loudness and analyze-spectrum (the consumers) share with this library: running a consumer's tests from a git worktree, taking test results for each commit of a pull request, and driving the real app on macOS without synthesized mouse or keyboard input. The last two sections say how this library's CI runs and what the consumers' workflow for an ffmpeg update does. Below, `<package>` is `analyze_loudness` or `analyze_spectrum`, and `<product>` is the folder name `settings_dir()` receives (`analyze-loudness` or `analyze-spectrum`).

## Testing a consumer from a worktree

- A new worktree of a consumer has an empty `vendor/py-analyze-common`. Run `git -C <worktree> submodule update --init` first.
- The consumer's `.venv` holds an editable install of the main checkout, so run the tests with `PYTHONPATH=src <main checkout>/.venv/bin/python -m pytest` from the worktree, and print `<package>.gui.__file__` once to confirm which tree was imported.
- To test against a py-analyze-common worktree that is not committed or not merged yet, list its `src` first and the consumer's own vendor path after it: `PYTHONPATH=<shared worktree>/src:<consumer worktree>/vendor/py-analyze-common/src:src`, with absolute paths. The consumer's `src/<package>/__init__.py` inserts the vendor path at the front of `sys.path` only when it is not there already, so with the vendor path listed, the shared worktree stays in front. This reaches the Python imports only. The consumers' frontend tests load the shared files under `web/` by file path from `vendor/py-analyze-common` (`tests/frontend/test_ui.html`), so a change to those files is tested with the overlay below.
- The other way is to lay the shared worktree's files over the submodule: `rsync` the shared worktree's `src/` into the consumer worktree's `vendor/py-analyze-common/src/`. Once the shared pull request is merged, `cmp` the copies against the merge commit before `git -C <consumer worktree>/vendor/py-analyze-common checkout -f --detach <merge commit>` replaces them. Before the consumer's own pull request is opened, the submodule is back at the commit the consumer's `master` points at ([Changes that span this library and the consumers](../AGENTS.md#changes-that-span-this-library-and-the-consumers)).
- The same overlay on a consumer's `master`, with the whole shared branch in `vendor/py-analyze-common`, is the test of the state the Dependabot submodule update makes before the consumer's own change arrives.

## Per-commit test runs

Test results for each commit of a pull request (for its body) come from a tree taken out of that commit, not from the working tree:

1. `git archive <commit> | tar -x -C <dir>`
2. Read the commit's submodule pointer with `git ls-tree <commit> vendor/py-analyze-common`, make a detached py-analyze-common worktree at it, and symlink `<dir>/vendor/py-analyze-common` to that worktree
3. Run `PYTHONPATH=src <main checkout>/.venv/bin/python -m pytest` from `<dir>`. Without `PYTHONPATH=src` the `.venv`'s editable install imports the main checkout's package, not the commit's. Print `<package>.__file__` and `analyze_common.__file__` once to confirm that both come from under `<dir>`

analyze-loudness sets no `testpaths` in its `pyproject.toml`, so a run from `<dir>` also collects the tests under `vendor/py-analyze-common` and its counts are larger; analyze-spectrum's `testpaths` is `["tests"]`. A rebased branch needs the runs again.

## Probing the real app on macOS

The real GUI can be driven end to end from inside its own process: the page's own fetch and POST paths run in WKWebView, and no mouse or keyboard input is synthesized.

### Keeping the user's settings out of a probe

- On macOS `settings_dir()` builds the settings folder from `Path.home()`. Start the app with `HOME` pointing at a temp folder that holds `Library/Application Support/<product>/settings.json`, and the user's own settings file is neither read nor written.
- A probe that imports `<package>.gui` into its own process (a script that calls `gui.main()`, or a Playwright probe that serves the handler in-process) writes the real settings file as soon as the page's theme or language button is pressed, because the press POSTs `/settings`. Point `gui._settings.path` at a temp file, or, before importing `gui`, replace both `analyze_common.settings.settings_dir` and `analyze_common.update.settings_dir` with a function that returns a temp folder, as `_isolated_settings` in the consumers' `tests/conftest.py` does. Assert that the store's path is under the temp folder before the page loads.
- Choose stored values opposite to the operating system's (`defaults read -g AppleInterfaceStyle`, `defaults read -g AppleLanguages`). With the same values, a capture cannot tell a stored value from the default the page takes from the operating system.

### Driving the page

- Run from source: replace `webview.start` with a function that passes a `drive` function to the real one (`lambda **kw: real_start(drive, **kw)`), then call `gui.main()`. `drive` runs outside the window's thread. After `gui._window.events.loaded.wait()` it calls `evaluate_js`, for example to put a value in `#url-input`, call `requestSubmit()` on `#analyze-form` and wait for `#results .title-row`, or to click `#theme-toggle`. `window.destroy()` closes the window.
- A built `.app` takes no `evaluate_js` from outside. Start `Contents/MacOS/<executable>` directly with only `HOME`, `TMPDIR` and `PATH=/usr/bin:/bin` in its environment, which separates it from the user's settings and from an ffmpeg outside the bundle. To operate its page, copy the `.app` and add one script of the same origin to the copy's `frontend/index.html`. The script can hand its results out by sending them to the app's `/upload` under a `.wav` name: the app writes the upload under `TMPDIR`.

### Capturing the window

- Find the window number with Quartz `CGWindowListCopyWindowInfo` by the process ID, then `screencapture -x -l<number> <output>`. The image includes the window's shadow (`-o` leaves it out) and has twice the window's size in pixels on a display with a scale of 2. The process that runs `screencapture` needs the Screen Recording permission.
- For a settled window, repeat the capture once a second until two captures are byte-identical. That does not show what the window looked like while it launched: the colors during a launch are read from the first frames, as in semnil/py-analyze-common#14.
- A window that opens under the real pointer shows a tooltip (`.tip-popup`) over the page. Hide it with CSS before the capture.
- With more than one display, choose the display with `webview.create_window(..., screen=webview.screens[i])` and record `window.devicePixelRatio`. A canvas font size includes the scale, so a value that depends on the display differs between displays.

### The README screenshots

`docs/screenshot.png` of each consumer is a capture of the real app's window made this way: dark theme, Japanese, the same source in both apps, the default window size (1200 x 900). Before taking it, confirm that the pull requests of the UI it shows are merged, or that the tree is in the same state.

### Probes whose result depends on the launch

In the real WKWebView window, the page moving to the top when the window's width changes while the URL field has the focus (`_afterResize()` in [Shared frontend scripts](architecture.md#shared-frontend-scripts-web)) happens in some launches of the same build and not in others. Run a probe of it in three or more launches per app; one launch in which the page did not move can read as "fixed".

## CI of this library

CI (`.github/workflows/ci.yml`) runs on PRs and on pushes to main: its matrix runs on Ubuntu 24.04 (`test`) and macOS 26 (`test-macos`) with `fail-fast: false`. Each installs `pip install -e . pytest pytest-cov` on Python 3.12, runs `python -m pytest -q --cov --cov-report=xml` and hands `coverage.xml` to the job `coverage` as an artifact. The checks `test` and `test-macos` are required checks of main. The job `test-tempdirs-windows` runs `tests/test_tempdirs.py` on Windows Server 2025 and hands its report over in the same way; it is not a required check of main. Once all three reports exist, `coverage` uploads each to Codecov with `codecov/codecov-action`, and `.github/codecov.yml` sets `codecov.notify.after_n_builds: 3`, so Codecov posts its statuses from all three reports rather than from the ones that arrived first; Codecov combines the uploads for the same commit. The job's `id-token: write` lets the uploads authenticate with GitHub's OIDC token (`use_oidc: true`), so the repository holds no Codecov token. On a pull request a failed upload fails `coverage` (`fail_ci_if_error: true`); on a push to main the step's `continue-on-error` leaves the run green (.github/workflows/ci.yml:128). `codecov/project` is a required check of main, reported by Codecov once the three uploads have arrived; `codecov/patch` is not. The artifacts hand the reports over within one run and are kept for a day. Codecov does not process a report more than 12 hours older than the `timestamp` coverage.py writes into its XML (`codecov.max_report_age`, left at its default), so re-running the failed `coverage` job reuses the reports only within 12 hours of the test run; after that, re-running all jobs makes them again.

## Patch release for an ffmpeg update

What the consumer's `.github/workflows/ffmpeg-watch.yml` does, job by job. Its prerequisite and what a person does are in `AGENTS.md`, under the same heading.

1. detect: checks out the current tip of master when the job starts, including its tags and history, then compares `build_assets/ffmpeg.json` with the osxexperts.net page ([Bundled ffmpeg pin](../AGENTS.md#bundled-ffmpeg-pin-ffmpeg_release)). When the page has a different build, it confirms that BtbN has the same series and checks the SHA256 of both files, and makes a new pin. It makes a patch release when `__version__` equals the latest `vX.Y.Z` tag and either the pin changes this time or the current pin differs from the pin that tag released (the pin file in the tag, or, when the tag has none, the pin from when the file was first added after the tag)
2. smoke: checks out the exact commit recorded by detect, then on macOS and Windows runners, runs `tests/test_ffmpeg_binary.py` on the binaries fetched with `build.py --ffmpeg-only` using the pin from that commit, replaced by the candidate artifact when `pin_update=true`
3. land: opens in order the pin PR (`ffmpeg-watch/pin-<series>-<run id>-<attempt>`) and the bump-only PR (`ffmpeg-watch/bump-v<version>-<run id>-<attempt>`, `chore: update the version to vX.Y.Z`), pushing and opening them and enabling their auto-merge with the GitHub App's token (the prerequisite is in `AGENTS.md`, under the same heading) and reading the PRs and runs with GITHUB_TOKEN. Each PR starts its CI (`Test 🧪`) and `dependabot-auto-merge.yml` (`auto-merge`) runs of `pull_request` and its `workflow-checks.yml` (`action-pins`) run of `pull_request_target`; once the three runs on its head commit succeed, land enables auto-merge on that commit (`gh pr merge --auto --merge --match-head-commit`) and waits for GitHub to merge the PR, which GitHub does once every required check of master's ruleset passes. One of them, `codecov/project`, is reported by Codecov after the CI run, and `gh pr checks --required` lists only the checks already reported, so a merge made on that command's answer can come before `codecov/project` has reported, and the ruleset refuses it. After the bump's merge, `tag-release.yml` tags the merge commit when the CI run of the push to master succeeds (step 2 of the [Release procedure](../AGENTS.md#release-procedure)). GITHUB_TOKEN is not used for these PRs: a PR it opens starts no `pull_request_target` run and its `pull_request` runs wait for an approval, and the checks of runs started with `workflow_dispatch` are not counted as the required checks of master's ruleset (the merge of such a PR was refused with `3 of 3 required status checks are expected.`)
4. A person publishes the Release (step 4 of the [Release procedure](../AGENTS.md#release-procedure))

- When a PR from an earlier run (an open PR whose head is `ffmpeg-watch/`) remains, land fails without changing anything. Close or merge that PR, then run again. The branch name differs per run (run id and attempt), so a branch pushed by a run that failed before opening its PR does not collide with the next run's push (that branch stays without a PR). When only the pin PR was merged and the bump remains, the next run's detect resumes from the bump, as "the current pin differs from the pin the latest tag released". When the bump was merged but there is no tag (for example, the CI run of that push failed), the next run's detect reports the master commit that set `__version__` to that value (`release_sha`), and land passes that commit and starts `tag-release.yml`. If the tag already exists, it does nothing
- When smoke, or any of the runs of a PR (CI, auto-merge, action-pins), fails, or a run does not start within three minutes, land stops at that point and does not merge
- While land waits for GitHub to merge a PR, a required check that fails, the PR closed without merging, and ten minutes without a merge each stop land. Once land has enabled a PR's auto-merge, whatever ends the land step before the PR is merged or closed (one of those stops, a command that fails, the SIGINT the runner sends the step of a cancelled job) makes the step call GitHub to turn that auto-merge off on the way out, so a check that passes later does not merge the PR; when that call fails, the step fails with the error `could not turn the auto-merge of #<number> off, so it can still merge`. On a cancelled job the runner ends the step's shell with SIGTERM 7.5 seconds after the SIGINT (actions/runner `src/Runner.Sdk/ProcessInvoker.cs`), and the step does not wait for a call still running then: if that call does not complete, the auto-merge stays on and no error is reported
